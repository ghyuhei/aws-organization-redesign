1. 要点

  1. 新しい組織が必要かを最初に判断する。必要なのは管理アカウント（支払元）を変える場合だけで、既存組織の管理アカウントは変更できない[1]。それ以外は既存組織の中で作り直す（方式 0）。組織を移さないので、Identity Center の URL も RAM の共有も変わらない。
  2. OU は AWS ホワイトペーパーの推奨に沿って作り、Control Tower（ランディングゾーン 4.0）で統制する。業務を止めうる統制は、4.6 の確認を済ませたアカウントにだけ効かせる。
  3. 新組織へは「アカウントの直接移行」で移す[2]。移したアカウントは Root 直下に入り、その時点で新組織のポリシーが効く[3][4]。そのため Root には、移ってきたアカウントの動作を変えないポリシーだけを付ける。旧組織の Control Tower に登録しているアカウントは、移す前に登録を外す必要がある[5]。
  4. システムが止まる原因は 3 つに分かれる。共有が外れる（Resolver ルール、VPC 共有など）、権限の条件が合わなくなる（組織 ID など）、組織の自動化が設定を変える（StackSets、Firewall Manager、Control Tower など）。7 章の方法で全件を洗い出し、移行の前に打ち消す。
  5. RAM で共有している TGW・Resolver ルールなどは、組織が変わっても外れない「ブリッジ共有」を先に作って移る。2026-02 に提供が始まった設定を使う[6][7]。VPC 共有は組織内でしか使えないので[8]、移行前に依存をなくす。
  6. 新組織では Identity Center の URL が必ず変わる。会社のドメインの URL を先に入口にして、ブックマークを守る。
  7. 影響がないことは計測で確認する。本番と同じく組織の境界をまたぐパイロットで unverified: の項目をすべて確認してから、本番に進む。

3. OU とアカウント

AWS ホワイトペーパーの推奨 OU[16]から、最初から必要なものに絞った。OU は組織図ではなく、同じ統制を受ける単位で分ける。Control Tower 4.0 では Security OU は必須ではないが、サービス連携に使うアカウントは同じ親 OU に置く必要がある[17]。

Root-Guard で招待の承諾も拒否する理由：直接移行では、移行先から届いた招待をアカウント側で承諾するだけで組織を移る[3]。離脱の拒否だけでは足りない。LeaveOrganization の権限が要るかは、公式ドキュメントの中で記述が分かれる。移行のページは直接移行では不要とし[3]、招待の承諾のページは組織のメンバーなら必要としている[35]（unverified: どちらが正しいか）。そこで両方を拒否する。

Root に付けた拒否は、その下のすべての OU とアカウントに効く[34]。切り戻しや事業の売却でアカウントを組織の外へ出すときだけ、変更管理のもとで対象アカウントを除外する条件（"StringNotEquals": {"aws:PrincipalAccount": ["対象のアカウント ID"]}）を加え、終わったら戻す。

4.4 RCP

RCP は、組織外のプリンシパルからのアクセスも止める。対象サービスは 60 を超えるが[20]、最初は S3・STS・KMS・SQS・Secrets Manager に絞る。公式ドキュメントも、影響を十分に試さずに Root へ付けないよう強く勧めている[20]。

RCP内容付与先
Perimeter-Core信頼する組織以外の ID によるアクセスを拒否する（aws:PrincipalOrgID）。AWS サービスによるアクセスは、自組織のリソースを起点とするものに限る（aws:SourceOrgID）[37]テスト用アカウント → 下位の OU → Transitional 以外の各 OU の順に広げる[20]
Enforce-TLSaws:SecureTransport が false のアクセスを拒否する[43]Transitional 以外の各 OU
  • STS はフェデレーションを対象から外す。sts:AssumeRoleWithSAML と sts:AssumeRoleWithWebIdentity のリクエストには aws:PrincipalOrgID が含まれない[44]。sts:* にかけると、GitHub Actions などの OIDC、EKS の IRSA[45]、IdP から IAM への直接の SAML が拒否される。STS には sts:AssumeRole だけにかけ、フェデレーションはロールの信頼ポリシーで絞る[44]。Identity Center が作るロールでは AssumeRoleWithSAML を使えない[46]（unverified: Identity Center 経由のサインインに RCP が影響しないこと）。
  • 移行期間中は、新旧両方の組織 ID を並べる。否定形の条件演算子に複数の値を書くと NOR で評価されるので[47]、両方を並べれば「どちらの組織でもない場合だけ拒否」になる。旧組織を削除したら旧 ID を外す。
  • 組織外からの正当なアクセスは、先に例外にする。IAM Access Analyzer の外部アクセスの検出結果で洗い出し[13]、aws:PrincipalAccount で除外する（D3）。ELB のアクセスログを受けるバケットが旧形式のポリシーなら、新形式に直してから付ける。旧形式は ELB の AWS アカウントをプリンシパルにし、新形式はサービスプリンシパルを使う[48]。
  • S3 のウェブサイトエンドポイントは HTTPS に対応しない[49]。TLS を強制する前に、公開コンテンツを CloudFront と OAC の配信に移す。
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "EnforceOrgIdentities", "Effect": "Deny", "Principal": "*",
      "Action": "s3:*", "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": {
          "aws:PrincipalOrgID": ["o-NEWORGID", "o-OLDORGID"],
          "aws:PrincipalAccount": ["111122223333"]
        },
        "BoolIfExists": { "aws:PrincipalIsAWSService": "false" } } },

      "Action": "s3:*", "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": { "aws:SourceOrgID": ["o-NEWORGID", "o-OLDORGID"] },
        "Null": { "aws:SourceAccount": "false" },
        "Bool": { "aws:PrincipalIsAWSService": "true" } } }

ブリッジ共有の手順

  1. 棚卸し：元の共有ごとに、リソース・利用者・権限・リージョンを記録する[B6]。
  2. 作成と承諾：同じリソースと利用者に、保持設定付きの共有を別に作る（1 つのリソースは複数の共有に入れられる）。利用者側で、移行の前に招待を承諾する[6][B6]。
  3. 移行：利用者を先に、所有者（Network アカウント）を最後に移す[B8]。元の共有は外れ、ブリッジ共有でアクセスが続く[6]。
  4. 正式な共有へ：所有者が新組織に入ったら、RAM の組織共有を有効にし、OU 宛の共有を作り直す。関連付けがすべて ASSOCIATED になったことを確認する[B6]。
  5. ブリッジ共有の削除：正式な共有が、リソース・利用者・権限をすべて含むことを確認してから消す[B6]。

unverified: 所有者が移るときにブリッジ共有が残ること。2022 年のブログでは、アカウント指定の共有が所有者の移行後も続いたとあるが[B2]、現行の仕様では確認できていない。

サブネットとセキュリティグループは組織内でしか共有できない[8]。共有が外れると、参加者の既存のリソースは動き続けるが、新しいリソースは作れない。ELB など AWS マネージドサービスの自動処理（Auto Scaling、ノードの置き換え）は、サブネットへの継続的なアクセスを要する場合がある[85]。共有は、参加者が組織を離れると外れ[6]、所有者が先に移った場合も外れる[B2]。

7.5 権限の条件

  • 条件キー：aws:PrincipalOrgID、aws:PrincipalOrgPaths、aws:ResourceOrgID、aws:ResourceOrgPaths、aws:SourceOrgID、aws:SourceOrgPaths[37]。組織 ID を指定した IAM ポリシーは、移行に合わせて更新が要る[3]。移行前に新旧両方の組織 ID を並べ、旧組織を削除したら旧 ID を外す[47]。
  • OU パス：パスはアカウントが属する OU の位置を表す[37]。新組織の中で OU を移っても変わるので、Transitional と配置先の両方のパスを並べるか、組織単位のパス（o-xxxxxxxxxx/*）にする。
  • 直す場所：S3 バケットポリシー、KMS キーポリシー、IAM ロールの信頼ポリシー、SNS・SQS・Lambda・ECR・Secrets Manager のリソースポリシー、AWS Backup のボールトのポリシー、EventBridge のイベントバスのポリシー、VPC エンドポイントポリシー、StackSets のロール、CloudWatch Logs の宛先ポリシー[92]、CloudWatch のアカウント間監視のシンクポリシー[93]、両方の組織の SCP と RCP。旧組織に残るリソースと新組織のリソースの両方を直す。
  • Identity Center のロール：割り当てで作られるロール（AWSReservedSSO_許可セット名_接尾辞）は、アカウントの割り当てがすべて消えると削除され、次の割り当てでは別の接尾辞のロールになる[94]。このロールの ARN を KMS キーポリシーや EKS の aws-auth ConfigMap で参照していて、IAM で作った代わりのロールがないと、AWS サポートに頼まないと戻せない[94]。移行の前に、IAM で作ったロールをこれらに加えておく。ほかのリソースポリシーは、新しい割り当ての直後に更新する。
  • 管理用のロール：旧管理アカウントからのアクセス用のロール（OrganizationAccountAccessRole など）は、移行しても自動では削除されない[3]。招待で参加したアカウントには、新組織の管理アカウント用のロールが自動では作られない[95]。移行の前に信頼先へ新組織の管理アカウントを加え、移行後に旧管理アカウントを外す。Control Tower に登録していたアカウントでは、登録を外すと Control Tower が実行ロールを削除して組織の管理用ロールを加え、移行先で登録すると新しい管理アカウントを信頼する実行ロールが作られる[5]。

7.7 人のアクセスと Identity Center の URL

方式 0 なら、Identity Center のインスタンスをそのまま使うので、URL もサインインも変わらない。方式 A では新組織に新しいインスタンスを作る。既定の URL（d-xxxxxxxxxx.awsapps.com/start）はインスタンスごとに決まるので、必ず変わる[66]。URL を新しいインスタンスへ引き継ぐ方法は、公式には見当たらない（unverified: 引き継げないこと）。インスタンスを削除すると、許可セット・アプリ・割り当ては戻せない[110]。そこで利用者の入口を会社の URL にし、切り替えを転送先の変更だけで済ませる。

  1. 会社の URL を入口にする（移行の前）：会社のドメインの URL（例：https://aws.example.co.jp）から今のポータルへ転送する。ブックマーク、社内ポータルのリンク、AWS CLI の sso_start_url をこの URL に替えてもらう。AWS CLI はこの形の URL を sso_start_url に使える[111]（unverified: 必要な CLI のバージョン）。
  2. 新しいポータルの URL を決める：新しいインスタンスの URL を、覚えやすいサブドメインに変える。変更は一度しかできない[66]。
  3. 移行期間は新旧を並べる：会社の URL を新旧両方へのリンクを載せた案内ページにするか、IdP（Entra ID など）のアプリ一覧に新旧 2 つを並べる。新しいインスタンス用に、SAML と SCIM の連携を別に作る[112]。
  4. 割り当てをすぐに適用する：移したアカウントは旧 Identity Center で使えなくなる[101]。許可セットは組織内のアカウントに割り当てるものなので[113]、定義をコードで用意しておき、参加を確認したらすぐに適用する。
  5. それまでの入り方を用意する：新組織の管理アカウント用のロール（7.5）と、IdP から直接フェデレーションする緊急用の経路（D5）を使う。後者は Identity Center を通らない[15]。
  6. 連携アプリを移す：Identity Center を使うアプリ（AWS のマネージドアプリや、Identity Center を IdP にした SAML アプリ）を、新しいインスタンスへ付け替える[B9][B10]（unverified: アプリごとの手順と停止の有無）。
  7. 最後に入口を切り替える：最後のアカウントとアプリを移したら、会社の URL の転送先を新しいポータルだけにする。旧インスタンスは、利用者とアプリの移行が済んだことを確認してから削除する。

8.3 アカウントごとの Go / No-Go

  • 7 章の対処がすべて適用済みで、適用後に 8.1 の指標が変わっていない。
  • ブリッジ共有の関連付けがすべて ASSOCIATED になっている[B6]。
  • 組織内でしか共有できない共有（VPC 共有など）への依存がない。
  • 旧組織の Control Tower の登録を、7.2 の手順で外してある。
  • 新組織の管理アカウント用のロールと、Identity Center の割り当ての定義ができている。KMS キーポリシーと EKS に IAM で作ったロールを加えてある。
  • 招待を送れる（アカウント数の上限、販売者の一致、委任管理者でない）。
  • 監視とログの経路が移行後も途切れない（7.8）。
  • 変更凍結が効いており、担当者が立ち会える。

8.4 移行当日：監視・中止・復旧

  • 監視：8.1 の計測に加え、RAM の共有の状態変化（EventBridge）と DisassociateResourceShare（CloudTrail）を通知する[B6]。
  • 中止基準：疎通か名前解決の失敗が 1 回でも出た、AccessDenied が基準値を超えた、ENI の作成エラーが出た、ELB の 5xx が増えた。1 つでも当てはまれば、次のアカウントへ進まない。
  • 復旧は前進修正を基本にする：移行後の問題の多くは、足りない許可や共有を足せば直る（条件への組織 ID の追加、共有の追加、割り当ての作成）。種類ごとに、直す手順とコードを事前に用意しておく。
  • 旧組織へ戻すのは最後の手段：戻すこと自体がもう一度の移行で、旧 Identity Center の割り当ての作り直しや、旧組織の自動化の再適用が起きる。新組織の Root-Guard が招待の承諾を拒否するので、対象アカウントを一時的に除外する必要もある（4.3）。手順をパイロットで確認した場合だけ選択肢にする（unverified: 戻せるようになるまでの待ち時間）。旧組織の設定（共有、条件、SCP）は、すべての移行が終わるまで変えない。
  • 体制：ウェーブの時間帯は変更を凍結し、ネットワーク・アプリ・セキュリティの担当が立ち会う。計画は AWS のアカウントチームと共有する。事例でも、AWS のサービスチームと連携して問題に対処している[B6]。

8.5 影響ゼロを保証できないもの

次に当たるシステムは、パイロットで影響ゼロを確認できない限り、方式 A では移さない。方式 B（新しいアカウントに並行して作り、DNS の重み付けなどで利用者の流れを段階的に移す。旧環境は戻し先として残す）で移す。

  • 組織内でしか共有できない共有（VPC 共有など）への依存を、移行の前になくせない。
  • Account Factory の VPC でワークロードが動いており、登録を外すとその VPC が削除の対象になる。
  • Identity Center 連携アプリの付け替えで、利用者のサインインが止まる。
  • 組織経由の Marketplace ライセンスに依存し、個別の配布に切り替えられない。
  • パイロットで、unverified: の項目の影響を確認できなかった。

10. 運用と定着

  • ポリシーはコードで管理する：SCP・RCP・宣言型ポリシーを Git で管理し、セキュリティ担当と CCoE の 2 名で承認する。適用はパイプラインからだけ行う。
  • 変更は段階的に広げる：Policy Staging の子 OU → 対象 OU の 1 アカウント → 対象 OU の順に広げる[118]。SCP を絞るときは、IAM の「サービスの最終アクセス」を根拠にする。Organizations の単位でも確認できる[19]。
  • 例外：Exceptions OU への移動で表し、期限と責任者を台帳に記録して、四半期ごとに見直す。
  • 利用者への説明：EC2 ポリシーのエラーメッセージに社内 Wiki の URL を入れる[53]。ガードレールの一覧と例外の申請手順を公開する。移行の前に、会社の URL、新旧ポータルの使い分け、AWS CLI の設定の変え方を周知する。
  • 役割分担：CCoE は OU とポリシー、セキュリティは RCP・検知・例外の承認、ネットワークはハブと共有の移行、アプリの担当は棚卸しとウェーブの立ち会いを受け持つ。
  • 指標：配置先の OU にいるアカウントの割合、有効な例外の数、ガードレールによる AccessDenied の件数、アカウントの払い出しにかかる日数。
